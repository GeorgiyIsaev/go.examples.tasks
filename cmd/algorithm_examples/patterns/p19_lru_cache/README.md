## 1. Что это

**LRU Cache** — «кэш с ограниченной вместимостью, где при переполнении
выбрасывается тот элемент, который **давно не использовался**». Здесь
«использование» = последний вызов `Get` или `Put` на этот ключ.

Это не паттерн отдельной алгоритмической задачи — это дизайн-структура,
которая сочетает две структуры данных:

- **хэш-мапа** `key → узел` — для O(1) поиска;
- **двусвязный список** от most-recent к least-recent — для O(1) перемещения
  и вытеснения.

Сложность: `Get` / `Put` — заявлено O(1). Память — O(capacity).

> **Почему LRU, а не «просто стек»?** Структура должна перемещать «использованный»
> элемент на верх **без линейного поиска** — для этого нужен указатель на
> элемент в середине, а → двусвязный список. Мапа даёт этот указатель.

## 2. Ключевая идея

**Инвариант:** в кэше всегда ровно `≤ capacity` элементов, в порядке «от
recent к oldest» — и мапа даёт прямой путь к любому узлу за O(1). При каждом
успешном `Get`/`Put` этот ключ становится most-recent.

Два «странных» момента, которые надо знать:

1. **ховост и голова — фиктивные.** Они не содержат данных, а лишь
   облегчают вставку/удаление без веток «если список пуст» и «если
   вставляем в начало/конец». Благодаря этому `insertAtFront` и `remove`
   одинаково работают для любого узла.
2. **вытеснение — это всегда удаление узла ПЕРЕД tail** (least-recent),
   потому что список растёт «от головы» в сторону tail.

> Запомни: **если capacity == 0 — ничего не храним (или Get всегда -1).**
> Это ок, корректность не должна ломаться.

## 3. Как узнать, что задача про этот паттерн

**Признаки:**

- «кэш/дизайн кэша», «ёжели capacity, выбрасывать LRU»;
- «поддерживать Get/Put за O(1)», «порядок использования при вытеснении»;
- упоминание «least recently used» или «most recently used»;
- « авторизован только один раз и затем только в order» — более простая
  очередь «в порядке», но часто уже LRU.

**Антипризнаки (не этот паттерн):**

- нужно **все элементы** без вытеснения → просто мапа/сет;
- нужен произвольный порядок без привязки к recent → очередь/стек/очередь
  prioritised (p17 heap);
- нужна **сложность не O(1)** — можно сделать проще и проще (в реальных
  задачах часто проще).

## 4. Словесный алгоритм (на слух)

### Вариант A — Get

1. Если ключа нет в мапе → вернуть -1.
2. Если есть: взять узел, **отцепить его от текущего места**
   (prev.next = n.next; next.prev = n.prev).
3. **Вставить его после головы** (самый recent): n.next = head.next;
   n.prev = head; head.next.prev = n; head.next = n.
4. Вернуть n.value.

> Запомни: **сначала ремот, потом инсерт-ат-фронт**.

### Вариант B — Put с вытеснением

1. Если capacity == 0 — выйти (ничего не сделать) или вернуть.
2. Если ключ уже есть → обновить значение и переместить его как в Get
   (rear, затем front).
3. Иначе:
   3.1. создать новый узел.
   3.2. вставить его после головы (самый recent).
   3.3. добавить в мапу.
   3.4. если len(узлов) > capacity → удалить LRU:
     - LRU — узел перед tail (tail.prev).
     - отцепить его (как remove), удалить из мапы по ключу.
4. Ровно capacity элементов осталось.

> Запомни: **новый первый раз — always most recent; вытесняем только когда
> уже перевысили capacity**.

### Вариант C — evictOne (старший)

1. lru = tail.prev.
2. if lru == head → return (should not happen when capacity > 0).
3. remove(lru) — отцепить.
4. delete(byKey, lru.key).

## 5. Мини-задачи устно (без кода)

1. Почему LRU кэш нельзя сделать только на хэш-мапе без списка?
2. Что произойдёт, если в Get мы забудем сделать «move to front»?
3. Какую пользу даёт фиктивная голова и tail?
4. Что получится, если capacity меняется в процессе работы? (Выкинуть
   лишнее? Добавить место?)
5. Что вернёт Get(ключ) сразу после Put того же ключа?
6. Почему при capacity == 0 Get должен вернуть -1 for all keys?
7. Что будет, если в evictLRU мы забудем удалить узел из мапы?
8. Почему «двусвязный» список, а не обычный односвязный (как быстрее
   удалить middle)?

<details>
<summary>Ответы (сверься после решения)</summary>

1. Мапа даёт доступ по ключу, но **не знает порядок**: без списка она
   не скажет, какой ключ был самым старым, и вытеснение стало бы O(n)
   по всей карте.
2. Порядок в списке перестанет отражать обращения: часто читаемый
   ключ останется стареть на своём месте и вытеснится первым,
   хотя по LRU он самый «свежий» — получится LRU по **вставке**, а не
   по последнему чтению.
3. Фиктивная голова и tail — это «фальшивые» узлы-хвосты: у настоящей
   головы нет предка, у хвоста нет наследника, и все ветки if по
   началу/концу исчезают — один и тот же код для любого положения.
4. capacity меняется не в этой задаче (LC1381 задан заранее), но если бы:
   при уменьшении — вытеснять до нового предела, при увеличении — ничего
   не делать, просто вырос «бюджет».
5. Вернёт значение и **не** добавит вторую запись: узел просто
   переносится в голову (обновление, а не дубль).
6. При capacity 0 любое добавление сразу вытесняется, и в мапе
   пусто — Get любого ключа обязан вернуть −1, а не паниковать.
7. Утечка памяти: список отпустил узел, а мапа держит указатель
   навсегда; ключ «найден», но его узла в списке уже нет — рассинхрон
   и неверный eviction (может упасть на удалении следующего узла).
8. Для удаления узла из середины односвязного списка нужен предыдущий
   узел — пришлось бы идти от головы за O(n); двусвязный хранит `prev`
   и удаляет/переносит узел за O(1), зная только его адрес.

## 7. Ловушки на собесе

1. **Capacity == 0:** нельзя просто игнорировать — нужно, чтобы `Get`
   всегда возвращал `-1`, а `Put` — ничего не хранил.
2. **Забыли удалить из мапы при evict:** тогда мапа растёт, а `Get`
   не поймёт, что элемент удалён.
3. **«Put нового увеличивает size, но без проверки capacity»:**
   кэш может расти без вытеснения, и тогда evict не сработает.
4. **Дубликат ключа + вытеснение:** если ключ уже есть, сначала
   обновляем и перемещаем, потом (если `len(byKey) > capacity`) —
   evict, но evict не должен трогать этот же элемент (он уже most recent).
5. **Ошибка при отцеплении:** если неправильно настроить `prev.next`
   / `next.prev`, список ломается — один узел «теряется» или
   появляется цикл.
6. **Ориентация порядка:** most-recent — самый левый (после head),
   least-recent — самый правый (перед tail). Перепутал — вытеснит
   не того.
7. **Размер:** можно полагаться на `len(byKey)` или вести отдельный
   счётчик — но если ведёте счётчик, он должен обновляться синхронно
   с мапой.

## 8. Шаблон кода для собесе

```go
// Узел кэша в двусвязном списке.
type node struct {
	key   int
	value int
	prev  *node
	next  *node
}

// LRU-кэш с фиктивными head/tail.
type LRUCache struct {
	cap   int
	head  *node
	tail  *node
	byKey map[int]*node
}

func NewLRUCache(capacity int) *LRUCache {
	if capacity <= 0 {
		capacity = 0
	}
	head, tail := &node{}, &node{}
	head.next = tail
	tail.prev = head
	return &LRUCache{
		cap:   capacity,
		head:  head,
		tail:  tail,
		byKey: make(map[int]*node, capacity),
	}
}

func (c *LRUCache) Get(key int) int {
	n, ok := c.byKey[key]
	if !ok {
		return -1
	}
	c.moveToFront(n)
	return n.value
}

func (c *LRUCache) Put(key int, value int) {
	if c.cap <= 0 {
		return
	}
	if n, ok := c.byKey[key]; ok {
		n.value = value
		c.moveToFront(n)
		return
	}
	n := &node{key: key, value: value}
	c.byKey[key] = n
	c.insertAtFront(n)
	if len(c.byKey) > c.cap {
		c.evictLRU()
	}
}

func (c *LRUCache) moveToFront(n *node) {
	c.remove(n)
	c.insertAtFront(n)
}

func (c *LRUCache) insertAtFront(n *node) {
	n.prev = c.head
	n.next = c.head.next
	c.head.next.prev = n
	c.head.next = n
}

func (c *LRUCache) remove(n *node) {
	n.prev.next = n.next
	n.next.prev = n.prev
}

func (c *LRUCache) evictLRU() {
	lru := c.tail.prev
	if lru == c.head {
		return
	}
	c.remove(lru)
	delete(c.byKey, lru.key)
}
```
