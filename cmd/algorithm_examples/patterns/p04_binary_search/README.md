# 04. Binary Search (Бинарный поиск)

## Что это

Бинарный поиск — это приём, когда мы **делим пространство поиска
пополам** на каждом шаге. Вместо O(n) линейного прохода получаем
O(log n).

Большинство думает, что это «поиск элемента в отсортированном
массиве». На самом деле бинарный поиск — это **метод решения задач**,
где есть:

1. **Монотонное пространство** — либо отсортированный массив, либо
   диапазон возможных ответов, где «подходит» — монотонная функция.
2. **Умение за O(1) определить, в какой половине ответ.**

## Ключевая идея: инвариант

Мы всегда поддерживаем интервал `[left, right]`, в котором **точно**
лежит ответ. На каждом шаге смотрим в `mid` и отбрасываем ту
половину, где ответа быть не может.

## Четыре подварианта

### 1. Классический поиск

Точное совпадение в отсортированном массиве.

```go
left, right := 0, len(nums)-1
for left <= right {
    mid := left + (right-left)/2
    if nums[mid] == target { return mid }
    else if nums[mid] < target { left = mid + 1 }
    else { right = mid - 1 }
}
return -1
```
Особенность: right = n-1, условие left <= right, обе
границы сдвигаются на mid ± 1.

Примеры: BinarySearch, SearchInsert, FirstBadVersion.

### 2. Границы (lower / upper bound)
   Ищем не «точное совпадение», а границу — первый элемент,
   удовлетворяющий условию.

```go
left, right := 0, len(nums)   // right = n!
for left < right {
mid := left + (right-left)/2
if nums[mid] < target { left = mid + 1 }
else { right = mid }      // right = mid, не mid-1
}
return left
```
Особенность: right = n, условие left < right, одна граница
сдвигается на mid+1, другая — на mid.

Примеры: LowerBound, UpperBound, SearchRange, CountOccurrences.

### 3. Повёрнутый массив
Массив отсортирован, но сдвинут влево на k позиций.

Идея: даже в повёрнутом массиве хотя бы одна половина
относительно mid отсортирована. По ней определяем, где искать.

```go
if nums[left] <= nums[mid] {
    // левая половина отсортирована
    if target в [nums[left], nums[mid]) { right = mid - 1 }
    else { left = mid + 1 }
} else {
    // правая половина отсортирована
    ...
}
```

### 4. Поиск по ответу (binary search on answer)
Самый мощный подвид. Мы ищем число — ответ задачи, а не
элемент массива.

Условия применимости:

Ответ лежит в известном диапазоне [low, high].

Есть монотонная функция feasible(x): «подходит ли ответ x».

Если feasible(x) истинно — истинно и для всех больших (или
меньших) x.

```go
left, right := low, high
for left < right {
    mid := left + (right-left)/2
    if feasible(mid) { right = mid }
    else { left = mid + 1 }
}
return left
```

Примеры: MySqrt, MinEatingSpeed, ShipWithinDays,
KthSmallest, SplitArrayLargestSum, Median of Two Sorted Arrays.

## Признаки, что нужен бинарный поиск
- 	Отсортированный массив и «найти X».
-	Слова «минимальный такой, что ...», «максимальный такой, что ...».
-	«Найти в повёрнутом массиве».
-	Задача на оптимизацию: «минимальная скорость», «минимальная
грузоподъёмность», «минимальное время».
-	Входные данные огромные, и O(n) не проходит.
-	Есть монотонность: ответ либо слева, либо справа от mid.

## Признаки, что НЕ нужен
-	Массив не отсортирован, и сортировка не окупается (O(n log n)
сортировки + O(log n) поиска = O(n log n), а можно решить за O(n)).
-	Нужны все элементы, удовлетворяющие условию.
-	Свойство немонотонно: например, «найти пик» с плато.


## Общий шаблон (запомните один раз)

```go
left, right := <начало диапазона>, <конец диапазона>
for <условие цикла> {
    mid := left + (right-left)/2
    if <ответ в левой половине> {
        right = <сузить влево>
    } else {
        left = <сузить вправо>
    }
}
return <left или right или nums[left]>
```

## Типичные ловушки
1.	Overflow в (left+right)/2.
      В Go int — 64 бита, но привычка писать left + (right-left)/2
      считается хорошим тоном. На Java/C++ без неё ловится overflow.
2.	Путать left <= right и left < right.
      o	<= — обрабатываем случай одного элемента (классика).
      o	< — не обрабатываем, но зато инвариант left == right = ответ
      (границы).
3.	right = mid vs right = mid - 1.
      Если пишете mid - 1 там, где нужно mid — потеряете ответ.
      Если mid там, где нужно mid - 1 — бесконечный цикл.
4.	Бесконечный цикл.
      Возникает, когда mid не двигает ни left, ни right. Проверьте:
      mid всегда должен быть либо < right, либо > left строго.
5.	Пустой массив.
      len(nums) == 0 — цикл не выполнится, но проверьте, что nums[0]
      нигде не читается до цикла.
6.	Ответ за границами диапазона.
      В SearchInsert right = n, а не n-1, потому что ответ может
      быть после последнего элемента.
7.	Binary search on answer — забыли про нижнюю границу.
      Например, в MinEatingSpeed минимум — 1, а не 0. В
      ShipWithinDays нижняя граница — max(weights), а не 0.
8.	feasible(x) не монотонна.
      Если feasible может быть true → false → true, бинарный
      поиск ломается. Всегда проверяйте монотонность на примерах.

## Связанные паттерны
      •	Two Pointers (p01) — тоже сближающиеся указатели, но без
      деления пополам. O(n) vs O(log n).
      •	Sliding Window (p02) — для подмассивов, не для поиска.
      •	Префиксные суммы (p18) — часто комбинируются с бинарным
      поиском (например, поиск в prefix-массиве).

## Мини-упражнение
Без подсказки:

Дан [1,2,3,4,5] и target=3. Найдите индекс классическим
бинарным поиском.

Дан [1,2,2,2,3] и target=2. Найдите первое и последнее
вхождение.

Дан [4,5,6,1,2,3] и target=1. Найдите индекс. Как вы
определите, какая половина отсортирована?

Найдите минимальное k, при котором k² >= 50. (Это binary
search on answer: feasible(k) = k*k >= 50.)

Даны piles=[1,1,1,100] и h=4. Какова минимальная скорость
Коко? (Ответ: 100, потому что за 3 часа можно съесть по 1
банану из каждой маленькой кучи, а последнюю кучу — за час при
скорости 100.)

### Обратите внимание на **два самых важных момента**, которые часто упускают:

1. **Два шаблона цикла** (`<=` с `mid±1` и `<` с `mid`). Держите их в голове как две отдельные «формы». Попытка использовать один шаблон для всего приводит к бесконечным циклам или пропущенным ответам.
2. **Binary search on answer** — самый частый источник hard-задач на собесе. Если увидите условие типа «минимальное X такое, что...», сразу думайте в эту сторону.
